# design-sync notes — Smarter Dog UI Kit

## Repo shape

This is not a published component library. `src/components/ui/` is an internal
UI-kit folder inside the main booking app (`smarter-dogs-smart-humans`), no
`package.json`/`dist`/`.d.ts` of its own. Synced via the **package** shape, with
every component pinned explicitly in `cfg.componentSrcMap` (bypasses the
empty-`.d.ts` problem — `exportedNames()` has nothing to read since there's no
shipped `.d.ts` tree). **33 components** (was 26 before the 2026-10-26 sync),
scoped to exactly the barrel exports in `src/components/ui/index.js` (not
every file in the folder — `ErrorBoundary`, `PageShell`, `NetworkOfflineBanner`,
`OfflineDemoBanner`, `ScribbleUnderline` live in the same directory but aren't
barrel-exported and were deliberately left out of this sync's scope).

## `cfg.entry` — REQUIRED, don't remove it (fixed 2026-10-26)

`cfg.entry` is set to `src/components/ui/index.js` (the barrel). This is
**load-bearing** for this repo's shape. Without it, `package-build.mjs` sets
`PKG_DIR = node_modules/smarter-dog-ui`, which does not exist (the UI kit is not
a real package), and the build crashes in `exportedNames()` with
`ENOENT … node_modules/smarter-dog-ui/package.json`. Pointing `cfg.entry` at a
real file inside the repo makes `PKG_DIR` walk up to the repo root (so
`cfg.srcDir` resolves) and gives esbuild the kit's public API surface to bundle.
The *previous* sync worked only because a hand-made `node_modules/smarter-dog-ui`
stub happened to exist at the time — `npm ci` deletes it, so that was never
reproducible. If a future diff shows `entry` missing, restore it; don't try to
rebuild the stub.

## New components added 2026-10-26 (26 → 33)

`Field`, `Input`, `Textarea`, `Select` (new form-control family — group

## cssEntry: now SCRIPTED (was hand-built) — `.design-sync/build-css-entry.mjs`

`cfg.cssEntry` (`.design-sync/.cache/compiled-tailwind.css`) is **not**
regenerated by the converter — it's built from a production build's dist CSS
because this app uses Tailwind v4's CSS-first `@theme` config (`src/index.css`),
so classes like `bg-brand-yellow` don't exist as real CSS until Tailwind
compiles them. As of 2026-10-26 the rebuild is a **committed script** (no longer
a manual `cat` + hand-clean):

```sh
npm run build                           # produces dist/app/assets/*.css
node .design-sync/build-css-entry.mjs   # concat + clean + font-path rewrite
```

What the script does (read its header comment for the full rationale):
- **Combined-build path change:** CSS now lives in `dist/app/assets/` (nested
  under `/app/` since the domain cutover bundles the marketing site), NOT
  `dist/assets/`. Font url()s are `/app/fonts/…` and the files live in
  `public/app/fonts/` → rewritten to `../../public/app/fonts/…`.
- **Chunks concatenated:** `index-*` (Tailwind utilities + `@theme` tokens),
  `skeleton-*` (pulse animation), `CustomerApp-*` (portal tokens), and
  `PageHeader-*` — which is actually `dayCard.css` (the `.wallet-*` header
  LAYOUT, needed by `DayCard`).
- **Chunk DELIBERATELY EXCLUDED:** `TodayView-*` is `dayStack.css`
  (`.wallet-appointment{position:absolute}`). Including it collapses a
  standalone `DayCard` preview to zero height (it's the stack's positioning,
  not the card's own layout). `BookingWizard-*` is excluded too (not a UI-kit
  concern).
- **Noise stripped:** `.font-[…]` rules for `DM Sans`/`Sora` (arbitrary-value
  classes used elsewhere in the app — re-verify empty via
  `grep -rn "DM Sans\|Sora" src/components/ui/*.{jsx,tsx}`); the 4 Caveat
  subset `@font-face` blocks (Caveat ships via `cfg.extraFonts`); and the
  dangling `.text-[var(--sd-coral)]` rule (the `--sd-*` family was deleted).

The output IS committed (not gitignored), so skipping the rebuild just reuses
the last snapshot — only redo it when the app's Tailwind output actually
changed (new brand colours/fonts). The chunk hashes in the filenames vary per
build; the script matches by prefix so it doesn't matter.

  one-off arbitrary-value classes used elsewhere in the app. Stripped by the
  script. If the warning returns, re-verify with the grep above before fixing.

## Known render warns (triaged, safe to ignore on re-sync)

- `[RENDER_ERRORS]` on **ErrorBanner** and **InlineError**: false positive.
  `package-validate.mjs`'s render check treats any mount whose `textContent`
  starts with "⚠" as a caught render error (`t.startsWith('⚠')` at
  `lib/../package-validate.mjs` render-check block) — but both components
  legitimately render a real "⚠"/"⚠️" warning glyph as their OWN first
  character of content (that's their actual UI, not a thrown error). The
  "error text" printed is just their own message with the glyph sliced off
  (confirmed by manually loading the page with `page.on('pageerror', ...)` —
  no real error fires; the glyph-prefix heuristic is the whole story).
  Not a bug in these components — don't try to "fix" it by removing the
  glyph or changing markup.

- `[TOKENS_MISSING]` (8 vars, 2026-10-26): `--fill-top`, `--fill-bottom-gap`,
  `--inbox-shell-top`, `--inbox-bottom-gap`, `--journey-centres` are set at
  runtime via inline `style`/JS — EXPECTED absent from static CSS, non-issue.
  `--sd-sky-tint`, `--sd-ink-light`, `--sd-navy` are leftover references to the
  **removed** `--sd-*` token family; confirmed NOT used by any synced component
  (`grep -rn "sd-sky-tint\|sd-ink-light\|sd-navy" src/components/ui/`), so they
  are dangling app-wide noise, not kit breakage. Non-blocking; don't chase.

## Grouping

No real component docs exist, so every component's `<group>` comes from a
`cfg.docsMap` stub (`.design-sync/docs-stubs/<Name>.md`, just
`---\ncategory: <group>\n---`) rather than discovered docs. Groups used:
`actions`, `surfaces`, `status`, `feedback`, `layout`, `data`, `loading`, and
`forms` (added 2026-10-26 for Field/Input/Textarea/Select).

## Authored-preview constraint: cssEntry only has classes the real app already uses

`cssEntry` is `dist/`'s compiled Tailwind output (see above) — it contains
**only the utility classes some real app page already triggers**, not the
full Tailwind utility set. A `.design-sync/previews/<Name>.tsx` wrapper `div`
that reaches for a class no real app page happens to use (e.g. `h-24` — not
used anywhere in this app today) silently renders with NO height, since the
class doesn't exist in the shipped CSS at all (caught this in `SkeletonBlock`'s
`Shapes` story — fixed by using an inline `style={{ height: 96 }}` instead).
**When writing wrapper markup in a preview, prefer inline `style` for any
arbitrary/uncommon sizing** rather than a Tailwind class you haven't verified
is already in `ds-bundle/_ds_bundle.css` — classes passed as real component
*props* (e.g. `variant="primary"` on `Button`) are safe, since those are
hardcoded literals inside the component's own source and guaranteed to be
compiled (the component is used somewhere in the real app). Verify any new
wrapper class with: `grep -o '\.<class-escaped>{[^}]*}' ds-bundle/_ds_bundle.css`
(escape `/` as `\/`, `.` as `\.` etc. — Tailwind escapes special chars in
selectors).

## guidelinesGlob deliberately empty

The default `guidelinesGlob` (`docs/*.md`, `docs/guides/**/*.md`) matches
against `PKG_DIR` — which is the **whole app's repo root** here (no separate
package dir), so it picked up the entire `docs/` folder: capacity-engine,
migrations, whatsapp-agent, staff-web-push, etc. Those are the booking app's
internal engineering docs, not design guidance for this UI kit, and some
touch security-sensitive internals — irrelevant/inappropriate to ship into a
design system a design agent reads for building UI. Set to `[]` deliberately.
This kit has no real design-guideline docs of its own; if one gets written
later (e.g. a proper `docs/design-system/*.md`), point `guidelinesGlob` at
that specific path rather than re-widening it to the repo default.

## Re-sync risks

- **cssEntry rebuild is still a separate step** (now scripted:
  `node .design-sync/build-css-entry.mjs` after `npm run build`), NOT run by
  `resync.mjs`. A sync that skips it silently reuses the last snapshot (stale
  but not wrong). Always run it when `src/index.css`'s `@theme` block or any
  `src/components/ui/*` class usage changed since the last sync. The script's
  chunk-exclusion logic (keep `PageHeader-*`=dayCard.css, drop `TodayView-*`=
  dayStack.css) is the fragile part — if Vite re-groups CSS chunks in a future
  build, re-verify which chunk holds `.wallet-heading` vs `.day-wallet-stack`
  (the script's header documents the split).
- `componentSrcMap`/`docsMap` enumerate every component by name (not the
  usual "exceptions only" sparse pattern) because there's no `.d.ts` and no
  real docs at all — correct for this repo's shape, but needs a new entry by
  hand (plus a `.design-sync/docs-stubs/<Name>.md` stub and an authored
  `.design-sync/previews/<Name>.tsx`) whenever a component is added to the
  `src/components/ui/index.js` barrel. Check the barrel against
  `componentSrcMap` first thing each sync; `npm run check:design-sync` reports
  added/changed/removed component files.
- ⚠️ **`config.json` got reset to its committed state mid-sync on 2026-10-26**
  (an editor/linter restored the original, wiping the in-progress `entry` +
  new-component additions). If a build suddenly drops back to 26 components or
  crashes on `node_modules/smarter-dog-ui`, check `config.json` still has the
  `entry` key and the 7 new components before anything else.
- `Button`, `PageHeader`, `DayCard`, `MetricBar` are pinned `cardMode: "column"`
  in `cfg.overrides` (their multi-story exports render wider than a grid cell).
- **Orphan `quicksand-*.woff2` on the remote project** (left from the pre-2026-10-26
  sync, when Quicksand was the display font). The 2026-10-26 anchored re-sync left
  them because `deletePaths` only covers removed/regrouped *components*, and fonts
  aren't in that diff. They're inert (the current `styles.css` closure doesn't
  reference them). To sweep them on a future sync, add
  `fonts/quicksand-500.woff2`, `fonts/quicksand-600.woff2`, `fonts/quicksand-700.woff2`
  to the `finalize_plan` `deletes` list and `delete_files` them.


## Is the design system behind the code?

The design system is a snapshot. `.design-sync/token-snapshot.json` records the
CSS custom properties (src/index.css, src/customer-portal.css) and the shared
UI components (src/components/ui) it was last synced from, and one command
reports the difference:

```sh
npm run check:design-sync                    # report drift; exit 1 if there is any
npm run check:design-sync -- --update        # record the working tree
npm run check:design-sync -- --from <sha>    # record a past commit
```

After every `/design-sync`, run the `--update` form so the record moves with it.
The snapshot was first built from `c9c81be`, the commit the design system was
synced from on 2026-10-25, so the first report lists everything that changed
since. It is deliberately not part of `npm run lint` or CI: tokens change in
feature PRs, and a red build on each would be noise. Run it before a release, or
whenever the design system's README looks stale.
