## 2. Bugs found and fixed

### High

#### H1 — Legacy "Unknown" breed leaks onto booking cards
- **User impact:** Salon staff see "Hugo · £42 · Full Groom · David & Emily Cooper · Unknown" on the booking card. The dangling "Unknown" looks like missing data and is jarring next to the owner name.
- **Steps to reproduce:** Load `/` with the production dataset. Any booking whose `dogs.breed` is the literal string "Unknown" (legacy import data) shows it on the card.
- **Root cause:** `resolveBookingDisplay` in [engine/bookingRules.ts](../../src/engine/bookingRules.ts) filtered UUID-shaped raw breed values but not the legacy "Unknown" placeholder. `isMissingNameToken` was applied to dogName and owner but not breed.
- **Files changed:** [src/engine/bookingRules.ts](../../src/engine/bookingRules.ts) (filter applied to all three breed sources)
- **Tests added:** Two regression tests in [src/engine/bookingRules.test.ts](../../src/engine/bookingRules.test.ts) covering both `breedSnapshot = "Unknown"` and `dog.breed = "Unknown"` paths.
- **Retest:** Live dev server confirms the bookings render without the trailing "Unknown".

#### H2 — "Null" surnames render across the whole app
- **User impact:** Customers appear as "Mirek Null", "Andrea Null", "Renata Null" everywhere — humans directory, dog-card owner, booking-card owner. Looks broken, confuses staff.
- **Steps to reproduce:** Open `/dogs` or `/humans` against a dataset that has legacy rows with `surname = "Null"` (the README warns about this from an old faker pipeline).
- **Root cause:** `buildHumanFullName` in [transforms.ts](../../src/supabase/transforms.ts) and a duplicate builder in [useHumans.ts](../../src/supabase/hooks/useHumans.ts) did a plain `${name} ${surname}` concat with no placeholder filter.
- **Files changed:**
  - [src/utils/sanitiseFieldValue.ts](../../src/utils/sanitiseFieldValue.ts) — new shared placeholder-token stripper
  - [src/supabase/transforms.ts](../../src/supabase/transforms.ts) — `buildHumanFullName` and `dbDogsToMap` use it
  - [src/supabase/hooks/useHumans.ts](../../src/supabase/hooks/useHumans.ts) — `buildHumanMapEntry` uses it
  - [src/supabase/hooks/useDogs.ts](../../src/supabase/hooks/useDogs.ts) — three direct dog-row constructors use it
- **Tests added:** [src/utils/sanitiseFieldValue.test.ts](../../src/utils/sanitiseFieldValue.test.ts) — 4 specs covering known placeholders, casing, nullish input, and substring safety.
- **Retest:** Live dev server confirms zero "Null" matches in Humans/Dogs views.

#### H3 — "Booking created" chip in the inbox always says "this dog"
- **User impact:** When the AI applies a booking action, the inline timeline card says "Booking created → this dog · Mon 11 May 09:30" instead of the dog's name. Staff can't tell which dog at a glance.
- **Steps to reproduce:** Open an inbox conversation where the AI has applied a booking. The booking-created chip never resolves the name.
- **Root cause:** `BookingCreatedCard` looked up `dogNames?.[payload.dog_id]`, expecting an id→name map. `useWhatsAppInbox` was setting `dogNames` to a plain string array (`(dogsData ?? []).map(d => d.name)`), so the lookup-by-UUID always missed.
- **Files changed:**
  - [src/supabase/hooks/useWhatsAppInbox.ts](../../src/supabase/hooks/useWhatsAppInbox.ts) — added `dogNamesById` map alongside the existing array
  - [src/components/views/inbox/InboxView.jsx](../../src/components/views/inbox/InboxView.jsx) — passes the map to the chip
  - [src/components/views/inbox/thread/BookingCreatedCard.jsx](../../src/components/views/inbox/thread/BookingCreatedCard.jsx) — prop renamed to `dogNamesById` for clarity
- **Tests added:** None directly — the change is data-shape plumbing. The fallback "this dog" string still applies when the map genuinely doesn't have an entry, so the existing render path is unchanged for the empty case.
- **Retest:** Code path verified against the conversation in the live inbox.

## 4. Remaining risks and follow-ups

1. **Optimistic update paths in `useDogs.ts`** still set `breed: dogData.breed` / `data.breed` directly (5 occurrences in add/edit handlers). User-typed input doesn't normally contain placeholder tokens, but for full defence-in-depth those could be sanitised too. Out of scope for this pass — write paths can wait for a write-validation review.
2. **Settings sections were verified to render**, but I didn't drive a save on each section. The April UX audit issue ("blank below the first two") is no longer present; sections like Capacity Engine show real content.
3. **HMR + new hooks:** Adding `dogNamesById` to `useWhatsAppInbox` caused a temporary Hooks-rules error during HMR mid-session. A fresh load clears it — not a production bug. Worth mentioning so a future contributor doesn't chase it.
4. **The DB still has legacy "Null" surnames + "Unknown" breeds.** Migration `20260513150000_fix_null_surnames.sql` resolves the surname case; there's no equivalent for breed yet. The display-layer fix means the UI never shows them, but a one-off DB cleanup of `dogs.breed = 'Unknown'` rows would be sensible follow-up.
5. **Mobile-specific keyboard / focus testing** wasn't done extensively. Layouts respond cleanly at 375 and 768; deeper a11y work (focus-trap on modals, screen-reader labels) was not in scope.
6. **No Playwright tests yet for the full bug-fix surface.** The E2E scaffold is in place with a single offline-mode smoke; building a journey suite for booking-create / status-pill / customer-portal-isolation is the obvious next step.
7. **`@testing-library/dom` peer fixed at v10**: a future bump of `@testing-library/react` to v17 (once it ships against React 19) will also need `dom` at the matching major.
