## Goal

Staff can read and answer an in-app conversation in the same inbox as WhatsApp. A customer who does not have the app still messages on WhatsApp exactly as they do today. Nothing in the website inbox changes until `VITE_APP_INBOX_ENABLED=1`.

## Why

The iPhone app needs a conversation that is not Meta. Staff already live in one inbox. A second inbox would split the queue. The messages have to be stored where a signed-in customer can read only their own, which the WhatsApp tables cannot do (staff-only select, phone-keyed, Meta-shaped).

## Current behaviour

WhatsApp and SMS threads are rows in `whatsapp_conversations` / `whatsapp_messages` (`channel` is `whatsapp` or `sms`). Staff read them in `/staff` inbox. Customers cannot select those tables. Sending is `whatsapp-send` (Meta) or `sms-send`. There is no in-app thread.

## Desired behaviour

- One app conversation per customer (`human_id`).
- Messages record the sender (`customer` or `staff`), the staff user when staff wrote it, the body, and when each side read it.
- Customers select only their own conversation and messages. Staff select all. Writes go through `send_app_message` and `mark_app_messages_read`.
- Realtime is on for both tables so the iPhone app and the staff inbox can subscribe.
- `list_staff_unified_inbox` returns one row per customer, with a channel list (`whatsapp`, `sms`, `app`). A WhatsApp number that is not linked to a customer stays its own row. `list_staff_unified_thread` returns the messages in time order, each with a channel.
- Replying to an app message sends `send_app_message`. Replying to WhatsApp still calls `whatsapp-send`.
- With the flag off, the website inbox does not call any of this.

## Scope

Migration `20261122120000_app_messaging.sql`, pgTAP `266_app_messaging.test.sql`, the staff inbox overlay, and `docs/app-inbox.md`.

## Non-goals

- No APNs and no staff Web Push for app messages. The insert is the hook; a later trigger can notify. Do not call `notify-staff` from `send_app_message`.
- No attachments. A later migration can add them.
- No iOS screens. The Swift skeleton does not call Supabase yet; sign-in is another change.
- No change to WhatsApp opt-out, templates, the 24-hour window, or `channelPolicy.ts`.
- No Edge Function. An Edge Function would deploy on merge to `main` before this migration exists in production. The RPCs are the API.
- Do not apply the migration to production in this change.

## Architecture

Postgres is the authority. The website overlay is a read model plus a send switch, and it no-ops when the flag is off or the RPCs are missing, so the WhatsApp list remains.

`send_app_message` and `mark_app_messages_read` are `SECURITY DEFINER` and check `auth.uid()` / `is_staff()` themselves. The list and thread functions are `SECURITY INVOKER` and raise `not_staff` for a customer, so they cannot bypass RLS.

## Data/database changes

New tables only. No change to `whatsapp_*` checks or policies. Authenticated gets `SELECT`. Inserts and updates are revoked; the definer functions write. `service_role` keeps table DML for a later server sender. Both tables join `supabase_realtime`.

## Migration/rollout

Expand-only. Safe to apply before the flag is on: nothing in the current website calls the RPCs. Apply on staging, then set the flag on a preview. Production apply is a separate, explicit step and is required before this can merge, because the migrations-applied check compares the file with production. This change does not perform that apply.

Rollback of the database, if staging needs it and nothing has stored real messages, is `drop table public.app_messages, public.app_conversations cascade;` plus dropping the four functions. Do not drop them on production once customers have threads.
