## Goal

Deliver an installable Smarter Dog iPhone app that supports the salon's daily
work using the existing booking system, with reliable session recovery, native
notifications and tested device interactions. Retain the browser experience.

**Recommendation:** use Capacitor to package the existing React application,
starting with a staff TestFlight pilot. Add the customer portal as a separately
scoped release after the shell and authentication are proven. Staff-first is a
planning assumption, not an existing product decision; customer-first would
reorder the feature milestones below without changing the server boundary.

## Why

The repository already contains substantial staff and customer workflows,
React UI primitives, Supabase integrations and mobile tests. Reusing them avoids
reimplementing business rules and maintaining a second presentation of every
booking state. The existing [iPhone plan](2026-10-27-iphone-interface-consistency.md)
identifies iPhone as staff's main device; its issue #1142 is closed, verified
through GitHub on 22 November 2026. A native shell should add dependable device
integration and convenient installation; merely loading the website is not the
acceptance criterion.

## Current behaviour and evidence

Repository observations at the base above, not a production audit:

- [package.json](../../../package.json) defines React 19, Vite, Supabase JS and
  PWA tooling. It does not declare Capacitor or React Native dependencies.
- [src/index.jsx](../../../src/index.jsx) and
  [entrypoints.ts](../../../src/routing/entrypoints.ts) select independently
  mounted staff, customer and password-reset routes. Staff enters through
  `/stafflogin` and `/staff`; customers through `/book`.
- [App.jsx](../../../src/App.jsx) composes staff auth, diary, Today, Inbox,

  includes authentication, profile/password setup, signup approval and booking.
- [client.ts](../../../src/supabase/client.ts) and
  [customerClient.ts](../../../src/supabase/customerClient.ts) separate staff and
  customer sessions. Staff auth explicitly documents an implicit-flow/password

- [LoginPage.jsx](../../../src/components/auth/LoginPage.jsx) and

- [Staff web push](../../staff-web-push.md) uses browser subscriptions, VAPID,

- [vite.config.js](../../../vite.config.js) builds PWA assets; sample data is a

- [PROJECT.md](../../../PROJECT.md) excludes native applications from the

  this is not proof that none exists.

## Desired behaviour

A staff member opens the app, signs in, checks Today, manages appointments and
reads/replies to messages. After suspension, the app refreshes server state
before enabling sensitive actions. Tapping a notification opens its authorised
booking or conversation, including after a cold start or expired session.
Denied notification/photo permission has a usable recovery path.

Customers in the later release can sign in, finish onboarding, manage dogs and
trusted humans, book and manage appointments with the same eligibility,
receipts and restrictions as the portal. Account deletion must be addressed
before distributing an app that supports account creation.

## Scope

- Bundled React assets in an iOS shell, native build configuration and repeatable
  simulator/device builds.
- Session storage, app lifecycle, safe links, keyboard/safe-area handling,
  native staff push and existing photo workflows.
- Staff pilot: Today, diary, booking detail/actions, Inbox, dog/customer lookup
  and account/device settings. Inventory remaining reports and owner settings;
  explicitly retain them or provide an authenticated web handoff.
- Customer release: current onboarding, approval gates, profiles, dogs, trusted
  humans, booking wizard, confirmation and appointment management.
- Native verification, release observability, TestFlight and distribution work.

## Non-goals

A SwiftUI rewrite, new booking policy, offline mutation queues, multi-tenancy,
autonomous AI expansion, a new payment processor, customer push notifications
or an automatic migration to visit commands. No production changes, Apple
account changes or application publication are performed by this planning task.

## Architecture

Propose Capacitor plus the existing React UI and Supabase clients. Keep native
integration behind a small `src/platform/` interface with browser and iOS
implementations for session persistence, lifecycle, links, push and media.
Place the native project in `ios/`, with a dedicated Capacitor configuration and
native Vite build mode. These paths are proposed, not existing implementation.

Bundle versioned assets; do not point the shipping shell at a mutable production
website. Native mode must bypass PWA service-worker/update behaviour and must
not depend on Vercel redirects. Keep the marketing website build independent.
Prove lazy assets, route basenames and cold-start deep links in the packaged app.

PostgreSQL remains final capacity authority under
[ADR 001](../../architecture/decisions/001-postgresql-capacity-authority.md).
Reuse existing authorised customer RPCs and staff repository paths; do not
introduce direct customer inserts or expose service-role credentials. Preserve
[ADR 002](../../architecture/decisions/002-separate-visit-authority-from-policy-activation.md)
and the roadmap STOP. Keep application separation consistent with
[ADR 009](../../architecture/decisions/009-independent-applications-in-one-repository.md).

Before selecting the framework, run a bounded device spike for CAPTCHA, auth
recovery, routing, keyboard and notifications. Record an ADR comparing Capacitor,
continued PWA delivery and a native UI. Recommend a different implementation only
if the spike demonstrates a requirement Capacitor cannot satisfy. Framework
versions, plugins and minimum iOS version must be checked against current vendor
support and the salon's actual devices; this plan does not invent those facts.

## Data/database changes

None for the shell and initial workflow reuse. Native push likely requires a
separate device-token table: authenticated staff owner, token, app identifier,
APNs environment, timestamps and revocation state. Specify uniqueness and
ownership-transfer rules before migration; restrict registration/revocation to
the authenticated staff member and sending to the backend. Do not overload
browser subscription endpoint/key fields with APNs tokens.

Use append-only migrations, RLS/grant tests and regenerated types. Extend delivery
logging only after checking its current channel constraints and dedupe semantics.
Keep native delivery independently flaggable. Rollback disables native sending
and registration while preserving existing web push and data; avoid destructive
down migrations. No backfill of customer records is needed.

## API changes

Existing booking/auth contracts remain the baseline. Add narrowly authorised
native device registration/revocation and APNs delivery support if the spike
passes. Preserve staff preference categories, actor suppression and event
deduplication, while separating per-device delivery attempts so a browser send
cannot consume a native device's delivery record.

Provider acceptance must not be labelled device delivery. Unknown send outcomes
must not trigger blind retries. Native links carry identifiers, never permissions;
resolve through the existing authenticated, role-checked data path. Review Edge
origin/CORS restrictions for the native origin without widening access globally.

## UI changes

Retain the current brand, shared controls and booking terminology. Adapt safe
areas, keyboard/composer placement, sheet heights, text scaling and navigation
for iPhone. Use at least 44-point touch targets and verify VoiceOver, focus,
reduced motion, contrast and large text on device.

Inventory every current booking state before changing screen composition,
including collected-but-unpaid, deposit warnings and uncertain message delivery.
Add explicit stale/offline states: network failure must never select demo data
or claim a booking succeeded. Keep photo library selection as a fallback when
camera permission is denied. Notifications are an opt-in after explaining value.

## Security/privacy considerations

Use an audited Keychain-backed storage adapter for native refresh/session tokens;
keep staff/customer namespaces distinct and clear the relevant session on logout.
Do not assume generic native preferences provide secure storage. Test refresh,
revocation and process death, and prevent tokens entering URLs or logs.

Test Turnstile in WKWebView at the real native origin before committing to the
login design. If it is unsupported, design a supported system-browser auth flow
with a reviewed return/session exchange; do not disable CAPTCHA, add wildcard
origins or silently switch auth flow. Validate recovery end to end.

Allowlist internal deep-link paths and external schemes, check auth before
navigation, and open external web content in the system browser. Recheck staff
membership on resume. Keep APNs keys server-side and notification payloads free
of customer names, phone numbers and message text by default. Review plugin
privacy manifests, analytics collection, private media handling and App Store
privacy declarations against actual code.

## Dependencies and risks

| Dependency or risk | Resolution / evidence |
|---|---|
| Staff versus customer first; one or two app identities | Product decision before bundle IDs and distribution setup; default proposal is staff pilot first. |
| CAPTCHA/recovery fails in embedded web view | Device spike is the first gate, with supported auth fallback design if needed. |
| Browser routing/PWA assumptions break packaged assets | Native mode, cold-start route tests and offline startup verification. |
| Suspended socket leaves stale appointments | Refresh/reconcile on foreground and reconnect; server checks remain final. |
| App Store review sees an insufficient wrapper | Demonstrate useful native integrations; review current Apple requirements before submission. Approval is not guaranteed. |
| Staff-only distribution unsuitable for a public listing | Evaluate custom/unlisted/public distribution against actual account and organisation eligibility. |
| Old app versions outlive backend releases | Additive contracts, explicit supported-build policy, tested update-required state and web fallback. |
| Concurrent shared UI/auth changes | Rebase and inventory current behaviour before each milestone; one writer for shared clients, migrations and notification sender. |
| Native signing and physical device testing | macOS/Xcode, representative iPhone and Apple Developer access required; unavailable in this planning verification. |

Existing iPhone consistency work (#1142) is closed; use its outcome as a baseline,
not a new dependency to redo. Check current issue status for any auth/design
work touched during implementation. Do not make the whole architecture
convergence programme a prerequisite; do not bypass its STOP either.

## Testing

For this documentation change, run `npm run check:docs` and `git diff --check`.
For implementation, run the repository bar:

```sh
npm run check:docs
npm run lint
npm run typecheck
npm run check:migrations
npm run test
npm run build
```

Run focused browser regressions with the deterministic sample-data configuration:

```sh
npm run e2e -- e2e/smoke.spec.ts e2e/viewport-continuity.spec.ts e2e/booking-modal-continuity.spec.ts e2e/interface-consistency.spec.ts
```

Retain the existing real-local-database customer suite described in
[customer-journey-tests.md](../../customer-journey-tests.md). Add native tests for
platform adapters and XCUITest journeys for cold launch, sign-in, session expiry,
logout and deep links. Record exact `xcodebuild` commands once the project scheme
and simulator target exist; Safari/WebKit tests alone do not prove WKWebView.

Native push changes also require `npm run check:edge-types`, relevant Deno tests
and `npm run test:db` for RLS/grants/uniqueness. Verify concurrent device
registration and duplicate dispatch in database/runtime tests. If any booking
write or locking changes become necessary, reassess scope and run
`npm run test:db:concurrency`; avoid changing those paths merely to package iOS.

Physical-device matrix: oldest supported and current iOS, small/large iPhone,
large text/VoiceOver, camera/photos denied, push denied, background termination,
poor network, expired sessions, duplicate taps and a stale booking race.
Use synthetic staging accounts; provider/device tests are separate from local
sample tests. Assert persisted outcomes for writes, including preserved payment
fields. No real customer messaging is needed for the pilot acceptance suite.

## Migration/rollout

1. Build and test locally with deterministic fixtures; validate server integration
   against a named non-production target and synthetic data.
2. Ship additive native-token schema and backend support before enabling the
   app feature; record exact target, migration and backend revisions. Preserve
   existing browser subscriptions and sender behaviour.
3. Verify APNs sandbox and production/TestFlight environments separately. Provision
   signing, associated domains and provider keys through the authorised release
   process; never commit them. Do not configure domains during planning.
4. Pilot with staff in TestFlight, record defects and acceptance evidence; keep
   native push independently disabled until its matrix passes.
5. Publish through the chosen distribution route after review. Record app version,
   build, Git SHA and compatible backend versions. Retain the web/PWA route.
6. On regression, disable the new backend capability, direct affected users to
   the web app and submit a corrected build. Installed binaries cannot be
   instantly rolled back; do not rely on a frontend redeploy to repair them.

## Observability

Record privacy-minimised app build/platform, startup and auth failure categories,
foreground refresh failures, notification registration/send outcomes and crash
reports. Keep booking mutation success distinct from notification status.
Establish pilot measurements before setting performance or reliability targets.
Never record tokens, customer text or full deep-link URLs in telemetry.

## Definition of done

- The chosen audience can install a signed build and complete the included core
  journeys on representative physical iPhones.
- Sessions, role boundaries, recovery and permission-denied paths are verified.
- App suspension/reconnection does not permit stale success claims or lost
  payment fields; server capacity and booking policy remain authoritative.
- Native push preferences, revocation, deduplication and authorised navigation
  work without regressing browser delivery.
- Native accessibility, crash/privacy review, required checks and browser
  regression checks pass; evidence names the exact app/backend revisions.
- Store/distribution requirements, support, compatibility and recovery are
  documented. Release approval and actual rollout evidence are recorded before
  this plan moves to completed.
