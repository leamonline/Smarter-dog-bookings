# 04 — Database, migrations, RLS, triggers, RPCs, Supabase platform

Auditor scope: data model and Supabase usage of `Smarter-dog-bookings` as of 12 October 2026 (239 migrations, HEAD includes `20261012120000`). Method: static reading of migrations, `src/supabase/database.types.ts`, `src/supabase/rpc.ts`, repositories/hooks and `supabase/functions`, **plus a full replay of the committed migration history into a disposable local Supabase stack** (`scripts/prepare-db-test-project.mjs` → `supabase start` → catalog dumps → `supabase test db`: **63 files, 1391 pgTAP assertions, all pass in 12 s**) and a handful of targeted experiments against that replayed database. No hosted project was touched. Where a finding was reproduced on the replay it is marked CONFIRMED; where it depends on production state the repo cannot show, HYPOTHESIS.

## 2. Findings

### F1. The 2-2-1 rule is not serialised across neighbouring slots for staff writes — CONFIRMED
**What.** `validate_booking_capacity()` (latest body: `20260919115000_no_show_is_not_an_uncancel.sql` L176–178) takes `pg_advisory_xact_lock(hashtextextended(booking_date || '|' || slot))` — a *per-slot* lock — before reading `get_seats_used()` for every slot of the day. The 2-2-1 rule is a *cross-slot* constraint (a rolling 3-slot window may hold at most 5 dogs), so two concurrent inserts into **different** slots each pass against the committed state and commit a state the engine forbids. A *per-date* lock does exist (`'booking_day_cap|' || date`, L181–184) but only inside `if not v_is_staff and booking_occupies_seat(new.status)` — it exists for the daily cap, not for 2-2-1.
**Evidence (replay).** Pre-state 08:30=2, 09:00=1, 09:30=1. Two sessions with a staff JWT (`request.jwt.claims.sub` = a `staff_profiles.user_id`) inserted into 09:00 and 09:30 concurrently; **both committed → 2,2,2**. `get_max_seats_for_slot(3, array[2,2,2,…])` = **1**, i.e. 09:30 is now over capacity. The same experiment as non-staff was correctly refused ("Capped at 1 (2-2-1 rule)") — only because both sessions happened to queue on the daily-cap lock. `scripts/verify-capacity-concurrency.sh` tests only the `same-slot` and `daily-cap` scenarios (L326, L502).
**Why it matters.** The DB is the documented source of truth for capacity; the frontend engine and the Deno copy both assume it is race-free. Service-role writers (WhatsApp agent/Flow) are non-staff and therefore serialised by accident; two staff devices (or staff + the overbooking override off) are not.
**Currently.** Low likelihood (one salon, few simultaneous staff writes) but a silent overbook when it happens; `booking_capacity_audit` would show two passing evaluations.
**Recommendation.** Take the per-date lock unconditionally, before any `get_seats_used`, and keep the slot lock (harmless):
```sql
-- in validate_booking_capacity(), replace the slot-only lock at L176 with:
perform pg_advisory_xact_lock(hashtextextended('booking_day|' || new.booking_date::text, 0));
perform pg_advisory_xact_lock(hashtextextended(new.booking_date::text || '|' || new.slot, 0));
```
Add a `cross-slot` scenario to `verify-capacity-concurrency.sh` (pre-state 2,1,1; contenders at 09:00 and 09:30; assert exactly one commits). Keep the per-date lock key distinct from `booking_day_cap|` or reuse it — either works; reusing it also simplifies the code. Mirror the lock in the three gate re-issues' "post-conditions" block so a later re-issue cannot drop it.
**Benefit.** Closes the only capacity race found. **Difficulty** Small. **Risk** Low (locks are xact-scoped; contention is one day's writes). **Priority** High.

### F2. Legacy table privileges: anon/authenticated hold INSERT/UPDATE/DELETE/TRUNCATE/TRIGGER/REFERENCES on core tables — CONFIRMED (replay) / HYPOTHESIS (prod identical)
**What.** `role_table_grants` in the replay: `anon` has `DELETE,INSERT,REFERENCES,SELECT,TRIGGER,TRUNCATE,UPDATE` on `bookings`, `humans`, `dogs`, `day_settings`, `salon_config`, `notification_log`, `whatsapp_*`, `staff_push_subscriptions`, … (every table created before `20260729000000`); `authenticated` the same. These are the pre-May-2026 Supabase defaults the CI prerequisite deliberately reproduces because production received them (`scripts/prepare-db-test-project.mjs` L18–33). RLS has no anon policies so row operations are denied — **but TRUNCATE is not a row operation and RLS does not apply to it.**
**Evidence.** `begin; set local role authenticated; truncate bookings cascade;` succeeded on the replay (NOTICE: cascades to `notification_log`, `groom_photos`, `whatsapp_booking_actions`, `booking_events`), rolled back. The Supabase advisor baseline has no finding for this class.
**Why it matters.** PostgREST does not expose TRUNCATE, so there is no API route today; the risk is defence-in-depth: any future permissive policy `to public`/`to anon`, any `SECURITY INVOKER` function reachable by anon, or a future surface (GraphQL, a mis-set `verify_jwt`) inherits full DML. `anon` needs **nothing** on any table (all public reads are SECURITY DEFINER RPCs).
**Recommendation.** One migration, verified by a pgTAP test modelled on `179_trigger_function_grants`:
```sql
revoke all on all tables in schema public from anon;
revoke truncate, trigger, references on all tables in schema public from authenticated;
alter default privileges for role postgres in schema public revoke all on tables from anon;
```
Then narrow `authenticated` per table to what its policies can ever permit (e.g. customers never INSERT `bookings`, so `revoke insert on bookings from authenticated` is safe only if `create_staff_booking_group` — SECURITY INVOKER — is accounted for: it runs as the caller and needs INSERT; keep INSERT for authenticated on `bookings`, `dogs`, `humans`, `day_settings`, `salon_todos`, `waitlist_entries`, `data_access_log`, `retention_marks`, `groom_photos`, `staff_*`). Run the full pgTAP suite and the E2E suite before applying; apply to staging first.
**Benefit.** Removes a whole class of latent exposure; aligns prod with the closed-by-default posture new tables already have. **Difficulty** Medium (the per-table narrowing needs care for the SECURITY INVOKER RPCs `create_staff_booking_group`, `search_*_directory`, `close_day_with_rearrangement_tasks`, `complete_closure_rearrangement_task`, `get_dog_grooming_intervals`). **Risk** Medium if rushed, Low with the pgTAP+E2E gate. **Priority** High.

### F3. The pregnancy gate is INSERT-only; UPDATE reschedules bypass it — CONFIRMED
**What.** `trg_enforce_dog_not_pregnant` is `before insert` only (`20260623130000` L78–80), unlike the calendar and capacity gates (`before insert or update`). Reschedules that UPDATE in place: `apply-customer-confirm/handler.ts` L481 (`.update({ booking_date, slot })`, service role ⇒ non-staff path) and the staff path (`useBookings.ts` L517, staff bypass anyway). The customer RPC path inserts replacement rows (`customer_reschedule_receipts.replacement_booking_ids`) so it is gated.
**Evidence.** Replay: mark dog pregnant, then `update bookings set booking_date=…, slot=…` as non-staff → "RESCHEDULE OF PREGNANT DOG SUCCEEDED"; a fresh insert for the same dog is refused with `DETAIL: pregnant`.
**Recommendation.** `create trigger trg_enforce_dog_not_pregnant before insert or update of booking_date, slot, dog_id on bookings …` (keep the `is_staff()` bypass). Add a pgTAP case to `010_booking_gates`.
**Benefit.** Gate parity with the other two; closes the WhatsApp-confirm reschedule hole. **Difficulty** Small. **Risk** Low. **Priority** Medium.

### F4. Deleting a customer with any booking history fails with an FK error, while the UI promises a cascade — CONFIRMED
**What.** Every booking insert creates a legacy visit and lineage (`aa_ensure_legacy_booking_visit` → `find_or_create_legacy_visit`). `booking_lineages.human_id` and `booking_visits.human_id` are `NO ACTION`, so `delete from humans` is refused for anyone who ever booked. `HumanCardConfirmDialogs.jsx` L37 says "dogs, bookings, photos all go too"; `useHumanMutations.ts` L396 does a raw `.delete()`. Conversely, for a human with dogs but no bookings, the `dogs→humans CASCADE` + `bookings→dogs CASCADE` chain hard-deletes history with no audit beyond `booking_payment_history`. `DogCardModal.jsx` L330 does the same for a dog ("bookings, photos, everything goes too") — and *that* one works, erasing the dog's bookings (and their capacity/report history) in one click.
**Evidence.** Replay: `delete from humans where id=…` → `ERROR: … violates foreign key constraint "booking_lineages_human_id_fkey"`.
**Why it matters.** Staff get an opaque error for the common case and a silent history wipe for the rare one. `humans.archived_at` / `dogs.archived_at` already exist (20260608130000/145000) and the directory filters on them.
**Recommendation.** Decide the policy explicitly: (a) make "Delete" in the UI an **archive** (set `archived_at`, cascade-archive dogs), and (b) provide one SECURITY DEFINER, owner-only `erase_customer(p_human_id)` RPC for GDPR erasure that anonymises `humans`/`dogs` columns and snapshot columns on `bookings`/`booking_events` instead of deleting rows (keeps capacity history and reports intact). Change `bookings→dogs` to `ON DELETE RESTRICT` so a stray hard delete is refused loudly. **Difficulty** Medium. **Risk** Low. **Priority** High (functional bug + data-retention policy gap).

### F5. Committed history still grants anon EXECUTE on seven SECURITY DEFINER functions the project's own checklist says to revoke — CONFIRMED (replay) / HYPOTHESIS (prod)
**What.** In the replay, `anon` can execute `apply_whatsapp_booking_action`, `mark_whatsapp_conversation_read`, `increment_conversation_unread`, `get_or_create_calendar_feed_token`, `revoke_calendar_feed_token`, `is_staff`, `is_owner` (plus the five intended public ones). The advisor baseline lists only the five intended, which means production either had these revoked out-of-band (the pattern `20260731100000` documented for trigger functions) or the linter missed them. The bodies of the first two check `is_staff()`/ownership, so this is hygiene, except F6.
**Recommendation.** A migration restating `revoke execute … from public, anon` for the seven, and a pgTAP test extending `179_*`: "no SECURITY DEFINER public function is executable by anon unless on this allowlist {get_public_open_days, get_public_salon_facts, get_public_holiday_notices, booking_policy_runtime, booking_policy_runtime_status}". This makes committed history the whole truth again. **Difficulty** Small. **Risk** Low. **Priority** Medium.

### F6. Dead, unauthenticated, anon-callable RPC `increment_conversation_unread(uuid)` — CONFIRMED
**What.** SECURITY DEFINER, no auth check, `grant execute … to anon, authenticated` (20260424001635), superseded by the `bump_conversation_unread` trigger in `20260424021708`; zero callers in `src/`, `supabase/functions/`, `scripts/`.
**Evidence.** Replay: `set local role anon; select increment_conversation_unread('0000…')` → succeeds.
**Impact.** Anyone with the anon key can inflate `unread_count` on any conversation id (nuisance, not data exposure). **Recommendation.** `drop function public.increment_conversation_unread(uuid);`. **Difficulty** Small. **Risk** Low. **Priority** Medium.

### F7. The inactive visit substrate: 28 tables, ~10.3k lines of SQL, 11 of the 31 `bookings` triggers, and stragglers from the status split — CONFIRMED
**What.** `20260726144000`…`144013` add 28 tables (29 of the advisor's `rls_enabled_no_policy` rows), 21+ trigger functions, 3 views, ~60 RPCs. `booking_policy_versions.previous_day_1500_v1.effective_at` is NULL ⇒ `booking_policy_runtime()` = `inactive`; `run_legacy_deposit_auto_release` and the projections branch on that. Of the 64 unindexed FKs and 49 unused indexes in the advisor baseline, ~55 and ~22 respectively are on these tables. 25 of the tables have **no code reference** in `src/` or `supabase/functions/` (reached only through RPCs/views). Every booking write still pays: `ensure_legacy_booking_visit` (2 lookups + visit/lineage upsert), `check_booking_visit_consistency` (3 lookups), `recompute_legacy_booking_visit` (aggregate + `for update`), `sync_visit_completion_from_child`, `record_booking_payment_history` (an insert per booking insert). At current volume (~600 bookings in 6 months) the runtime cost is negligible; the **maintenance cost is real**: the 20260919 status split (`Reconfirmed/Arrived/Ready for collection/No-show`) was not propagated into `recompute_legacy_booking_visit` (`status not in ('Cancelled','Completed')` ⇒ a `No-show` row keeps its legacy visit **`active`**) nor into `suggest_conversation_closures` (still matches `'Checked in','In bath','Ready for pick-up'`, which no longer exist, so `booking_confirmed_quiet` suggestions now miss three live statuses).
**Recommendation (not: activate the policy).** (1) Fix the two stragglers now by using `booking_occupies_seat()` — one-line changes. (2) Add a guard test: grep live `pg_proc.prosrc` for retired status literals (`'Checked in'`, `'In bath'`, `'Ready for pick-up'`) and fail if any remain — `228_contract_migration_against_real_rows` tests rows, not function bodies. (3) Record a decision (ADR) on the substrate's horizon: either a date by which `previous_day_1500_v1` is scheduled, or a contract plan that removes the money/ledger tables and keeps only `booking_visits`+`booking_lineages` (the parts the staff projections and change-request flow use). (4) Until then, do not add new FK indexes there; the advisor rows are correctly baselined. **Difficulty** Small (1–2) / Large (3–4). **Risk** Low / Medium. **Priority** Medium.

### F8. Free-text columns on `bookings` that the engine treats as enumerations — CONFIRMED
**What.** `bookings.service`, `bookings.payment` (`'Due at Pick-up' | 'Deposit Paid' | 'Paid in Full'` are matched literally in `recompute_legacy_booking_visit`, `run_legacy_deposit_auto_release`), `bookings.source`, `humans.source` have no CHECK. `create_customer_booking_group` accepts any non-empty `service` string (L~"v_service is null"); staff inserts too (replay: `service='Haircut Deluxe'` accepted). `resolveBookingDisplay`/pricing key on the four service names.
**Recommendation.** After `select service, count(*) … group by 1` on prod to learn the real domain, add `check (service in (...))` and `check (payment in (...))` as `NOT VALID` first, validate once data is clean. Keep `text`+CHECK rather than enums — the 20260919 contract migration shows why text is the easier type to evolve. **Difficulty** Small–Medium. **Risk** Low–Medium (unknown legacy values). **Priority** Medium.

### F9. `humans.customer_user_id` is not unique — CONFIRMED
**What.** Two indexes exist (`idx_humans_customer_user_id`, `humans_customer_user_id_idx`), neither unique. Every customer RPC resolves the caller with `where customer_user_id = auth.uid() limit 1` (e.g. `create_customer_booking_group`), so if `merge_humans`, `link_pending_signup`, `submit_customer_signup` or `link_customer_to_human` ever leave two rows linked to one auth user, which record books is arbitrary and RLS shows the user both.
**Recommendation.** Check prod (`select customer_user_id, count(*) … having count(*)>1`), then `create unique index concurrently humans_customer_user_id_uniq on humans(customer_user_id) where customer_user_id is not null;` and drop the two non-unique ones. **Difficulty** Small. **Risk** Low. **Priority** Medium.

### F10. Redundant indexes — CONFIRMED
`bookings_one_active_per_dog_slot (dog_id, booking_date, slot) where status∉{Cancelled,No-show,Completed}` is strictly weaker than `bookings_no_duplicate_dog_per_slot (booking_date, slot, dog_id) where status∉{Cancelled,No-show}` (drop the former — keep the one the trigger comments reference); `idx_humans_phone_unique_whatsapp_ai (phone) where source='whatsapp_ai'` ⊂ `humans_phone_unique`; `idx_humans_customer_user_id` ≡ `humans_customer_user_id_idx` (see F9). Harmless at this scale; each is an extra write per insert and a maintenance trap. **Difficulty** Small. **Risk** Low. **Priority** Low.

### F11. Phone uniqueness is on the raw string — CONFIRMED
`humans_phone_unique` indexes `phone` as stored; `humans_phone_mobile_shape` accepts both `07…` and `+447…` (digits-only regex), and the app strips only format characters (`stripFormatChars`, `useHumanMutations.ts` L110). `'07700 900001'` and `'+447700900001'` are two rows. `docs/migrations.md` says prod once had a generated `phone_normalised` column — it is not in the replay or the generated types, so either it was dropped or never committed. **Recommendation.** `alter table humans add column phone_e164 text generated always as (public.normalise_uk_mobile(phone)) stored;` + unique partial index; backfill duplicates through the existing `merge_humans`. **Difficulty** Medium (prod dedupe first). **Risk** Medium. **Priority** Medium.

### F12. Storage buckets: the configured one is unused, the used ones are unlimited — CONFIRMED
`supabase/config.toml` declares `dog-photos` (5 MiB, image/png|jpeg|webp) — no code references it. The buckets the app uses, `groom-photos` (`useGroomPhotos.ts`) and `whatsapp-media` (edge functions), are created by migrations with `file_size_limit = NULL`, `allowed_mime_types = NULL`. Staff can upload any file of any size to `groom-photos`. **Recommendation.** `update storage.buckets set file_size_limit = 10485760, allowed_mime_types = '{image/jpeg,image/png,image/webp,image/heic}' where id = 'groom-photos';` (and a sane limit on `whatsapp-media`); delete the `dog-photos` block from config.toml. **Difficulty** Small. **Risk** Low. **Priority** Medium.

### F13. Any authenticated non-staff user — including unapproved signups — can read the whole `salon_config` row — CONFIRMED
Policy `customer_select_salon_config` (`not is_staff()`) exists so the deposit panel can read bank details (`bookingsRepo.ts` L641). It also exposes `pricing`, `enforce_server_capacity`, `daily_dog_cap`, `whatsapp_provider`, `settings.businessPhone/Email`, notification channel config, and `bootQueries.js` L28 does `select *`. Nothing secret, but wider than needed and readable before approval. **Recommendation.** Replace with `get_customer_deposit_facts()` (SECURITY DEFINER, returns `bank` + `releaseHours`, refuses unless the caller's human is approved) and drop the table policy. **Difficulty** Small–Medium. **Risk** Low. **Priority** Low–Medium.

### F14. Three overlapping permissive UPDATE policies on `staff_profiles` — CONFIRMED (replay) / HYPOTHESIS (prod)
`Owners can update any profile`, `Users can update own profile`, `combined_update_staff_profiles` all exist in the replay (`20260330095239`, `20260414022627`, `20260422081058`). The last was meant to replace the first two; the retro-filed `20260414022627` says prod received a differently named version. Union semantics make the effect correct (own row, same role; owner any), but the advisor's `multiple_permissive_policies` would normally flag this — its absence from the baseline suggests prod differs from committed history here. **Recommendation.** Verify on prod (`select policyname from pg_policies where tablename='staff_profiles'`), then commit `drop policy if exists …` for the two legacy ones. **Difficulty** Small. **Risk** Low. **Priority** Low.

### F15. Time-zone handling is consistent except one UTC `current_date` — CONFIRMED
25 functions use `Europe/London` explicitly; `booking_date date` + `slot text` are wall-clock by design; cron jobs use the UTC-pair trick with `at_hour_uk` so DST is handled server-side. The one outlier: `request_customer_override_reschedule` uses `p_booking_date < current_date` (UTC). Between 00:00–01:00 BST this accepts London-yesterday as not-past (the calendar gate later refuses it for non-staff, so the effect is a worse error message, not a wrong booking). **Recommendation.** `((now() at time zone 'Europe/London'))::date` as in `validate_booking_calendar`. **Difficulty** Small. **Risk** Low. **Priority** Low.

### F16. Unbounded growth / retention is undefined for message and audit tables — CONFIRMED
`prune_measurement_telemetry` covers only `booking_funnel_events` and `booking_denials` (90 d); `prune_slack_alerts` covers `slack_alerts`. No retention for `whatsapp_messages` (full chat content), `notification_log.message_text` (rendered customer messages), `booking_events`, `booking_capacity_audit` (a row per booking evaluation), `booking_payment_history` (a row per booking insert), `whatsapp_events` (raw webhook payloads). Volumes are tiny today; the issue is a data-protection one (how long customer message content is kept), not performance. **Recommendation.** Write the retention decision down per table (ROADMAP/ADR), then one `prune_message_content()` cron that nulls `message_text`/`whatsapp_messages.body` older than N months rather than deleting rows (keeps the ledgers). **Difficulty** Small. **Risk** Low. **Priority** Low–Medium.

### F17. Migration ledger vs. objects: the gate catches ledger drift, not object drift — CONFIRMED
`check-migrations-applied.yml` compares the committed file (name + statements) with what prod recorded applying and is a required status check; `check-migrations-drift.yml` re-runs it daily; `check-advisors-drift.yml` diffs linter output against `supabase/advisors/baseline.json`. `docs/migrations.md` records ≥9 ledger discrepancies (3 pre-tracking files, 1 dashboard-applied, 5 prod-only rows of which 3 — `notification_log_idempotency`, `update_customer_dog_rpc_v2`, `fix_link_customer_to_human_phone_ambiguity` — are *function-level and have never been diffed*), and trigger-function grants were hardened on prod outside migrations until `20260731100000`. F5 and F14 above are exactly the shape of residue that process leaves. **Recommendation.** Add a weekly job that dumps prod's schema (`pg_dump --schema-only --no-owner --no-privileges` of `public`+`smarter_dog_private`, via the production workflow's existing credential) and the replayed CI schema the same way, normalises, and diffs — fail on any difference. The replay already exists (`db-tests.yml`); only the prod dump and the diff are new. **Difficulty** Medium. **Risk** Low (read-only). **Priority** Medium.

### F18. Outbound pg_net calls are fire-and-forget with no failure visibility — CONFIRMED
All 11 trigger/cron HTTP posts are wrapped (`20260916120000`, test `224`) so a Vault/pg_net hiccup cannot roll back a booking — correct. But a non-2xx *response* (e.g. edge function 500, wrong secret) is only recorded in `net._http_response`, which pg_net purges after ~6 h, and nobody reads it. Customer confirmations/reminders are compensated by `notification_log` + `notification-pending-reaper` + `reminder-sms-fallback`; staff push, Slack and the WhatsApp agent fire have no compensation. **Recommendation.** A `*/30` cron that counts `net._http_response where status_code >= 400 or error_msg is not null` in the last 30 min and inserts a `salon_todos` row / Slack alert through the existing `slack_alerts` ledger when > 0. **Difficulty** Small. **Risk** Low. **Priority** Low.

### F19. `waitlist_entries` has no uniqueness and each insert fires two outbound calls — CONFIRMED
Columns: `id, human_id, target_date, created_at`; policy lets a customer insert any number of rows for their own human; each insert triggers `notify_waitlist_joined_trigger` (pg_net) and `notify_staff_waitlist_joined` (pg_net). **Recommendation.** `create unique index waitlist_one_per_human_date on waitlist_entries(human_id, target_date);` and `check (target_date >= current_date)` is wrong (UTC) — use the RPC path or a London-date check. **Difficulty** Small. **Risk** Low. **Priority** Low.

### F20. `day_settings` JSON shape is only half-checked — CONFIRMED
`closures` has `jsonb_typeof = 'array'`; `overrides` (the seat-block map the capacity trigger and calendar gate read with `->` and `jsonb_each_text`) has no shape check, and `extra_slots`/`immediate_slots` have no `slots_are_hhmm()` CHECK (the helper exists and guards `humans.*_slots`). `active_slots_for()` sanitises at read time, so a bad write is tolerated rather than refused. **Recommendation.** `check (overrides is null or jsonb_typeof(overrides) = 'object')`, `check (slots_are_hhmm(extra_slots))`, `check (slots_are_hhmm(immediate_slots))`. **Difficulty** Small. **Risk** Low. **Priority** Low.

### F21. Hard-delete of bookings remains a staff capability — CONFIRMED
`staff_delete_bookings` policy + `useBookings.ts` L479 `.delete()`. `booking_events` keeps the orphan `booking_id` (no FK, by design), `notification_log`/`groom_photos`/`slack_alerts` SET NULL, `booking_payment_history` records the DELETE. Reports (2A–2F) and the daily-cap history lose the row; `Cancelled`/`No-show` already express every legitimate outcome. **Recommendation.** Restrict `DELETE` to `is_owner()` (or drop the policy and the UI action), keeping the owner-only path for genuine mistakes. **Difficulty** Small. **Risk** Low. **Priority** Low.

### F22. Query/index fit for the actual repository patterns — CONFIRMED (no action needed now)
Repositories filter `bookings` by `booking_date` (range), `dog_id in (…)`, `dogs!inner(human_id)`; `whatsapp_messages` by `(conversation_id, sent_at desc)`; `notification_log` by `booking_id`/`human_id`/`status`; `salon_todos` by `done`/`dog_id`. All have matching indexes (`idx_bookings_date`, `idx_bookings_dog_id`, `idx_dogs_human_id`, `idx_whatsapp_messages_conversation`, …). The customer `bookings` policy's EXISTS over `dogs`→`humans` is index-backed. The capacity trigger issues ~10–12 `get_seats_used` sub-queries per write (one per slot) — fine for a table measured in hundreds of rows per year; a single `group by slot` would be cleaner but is not worth a parity-fixture change today. No N+1 from the client was found: `useStaffAppData` loads by range and the customer portal by `dog_id in (…)`.

## 3. What is already done well

- **Table-level gates.** Calendar, capacity and pregnancy are `BEFORE INSERT` triggers on `bookings` (two of them also `UPDATE`), each `SECURITY DEFINER` with `search_path` pinned, each emitting a stable reason code in `DETAIL` (`20260826120000`) with post-condition blocks that fail the apply if the message set changes. Every write path — customer RPC, staff RLS insert, WhatsApp agent/Flow (service role), `apply-customer-confirm` — inherits them. This is the right design and it held under every experiment except F1/F3.
- **No customer INSERT policy on `bookings`; one customer write path** (`create_customer_booking_group`) that takes the authoritative size from `dogs.size`, refuses unconfirmed sizes, checks approval/profile completeness, and locks the requested slots.
- **All 233 SECURITY DEFINER functions have `search_path` set** — zero exceptions in the replay. Internal helpers (`validate_booking_calendar`, `get_seats_used`, `has_large_dog`, `reschedule_customer_booking_direct_unchecked`) have no API grants, and tests `179`/`232` guard the class.
- **RLS on every public table**, no anon row policies anywhere, `security_invoker` views, a private schema for receipts/history, a RESTRICTIVE deny policy on `whatsapp_manage_sessions`.
- **Concurrency primitives exist and are tested**: slot lock + daily-cap lock + per-customer reschedule lock + group-cancellation lock; partial unique index for the same dog/slot; `verify-*-concurrency.sh` scripts for same-slot, daily-cap, WhatsApp reschedule, holidays and dog-size races; `115_customer_cancellation_concurrency`.
- **Outbound HTTP is guarded** (`20260916120000`, test `224` sabotages `get_supabase_url()` and proves the write still commits); secrets come from Vault; `notification_log` has a partial unique idempotency index plus a reaper and an SMS fallback.
- **DST handled in the schedule, not the code**: UTC-pair cron jobs with `at_hour_uk` checks; 25 functions use `Europe/London` explicitly; `booking_date`/`slot` are wall-clock types.
- **Migration discipline**: idempotent `create or replace` + `drop … if exists`, post-condition `do $post$` blocks, the required `migrations-applied` check, daily ledger drift and advisor drift jobs, an advisors baseline with written rationale per class (`docs/supabase-advisors.md`), and a **full-history replay that boots and passes 1391 pgTAP assertions in 12 s** — the repository can rebuild its own database, which is rare.
- **Text + CHECK instead of enums** made the September status contract (`20260919*`) possible in one pass with row-level tests (`225`, `228`); keep it.
- **Trigger-function grant class** regressed three times and is now pinned by `179_trigger_function_grants.test.sql`; the same approach should be extended to anon-executable SECURITY DEFINER functions (F5).
